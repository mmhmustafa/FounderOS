# PR-178.1 — Table & Row Action Density

**Scan the Dataset. Act When Needed.**
*Audit and architecture. No code was modified. Nothing was committed.*

Measured against the running application at `f99382a` (post-PR-178) on the live 865-device
estate, at 375 / 768 / 1440 / 1920 px, plus a purpose-built two-discovery workspace to obtain
real `/changes` rows.

---

## 1. Executive diagnosis

### The premise needs correcting: tab stops are not the problem

The brief inherits a figure — *"~95 % of Policy's control count came from one repeated action
menu"* — and reasonably infers a keyboard and density catastrophe. Measured, the DOM count is
right and the inference is wrong. **A closed `<details>` removes its contents from the tab
order**, and Atlas's row menus are closed by default. Per row, Policy costs **3** tab stops and
Changes costs **1**.

| Page (50 rows) | DOM controls / row | **True tab stops / row** | Table DOM controls | **Table tab stops** | Table DOM nodes |
|---|---|---|---|---|---|
| Policy | 14 | **3** | 701 | 151 | 2,114 |
| Changes | 12 (+12 hidden inputs) | **1** | 600 | 50 | — |
| Evidence | 5 | **4** | 251 | **201** | 962 |
| Configuration | 4 | **3** | 200 | 150 | 660 |
| Timeline | 1 | **1** | 62 | 51 | 653 |

**The page with the fewest DOM controls per row has the most tab stops.** Evidence and
Configuration do not use the menu at all: they render `device_actions` **inline**, and every row
carries an accent-blue `#2563eb` "SSH" button — the same colour Atlas uses for primary actions.
Fifty of them per page.

> **Why the dataset reads as fifty control panels:** not because actions are hidden badly, but
> because on the pages that *don't* use the menu they are not hidden at all, and they are
> painted in the primary-action colour.

### Six measured defects

1. **Inline accent buttons in rows.** 50 `.btn-console` buttons per page on Evidence and
   Configuration, at `background: var(--accent)` / white text — visually identical to a page's
   one primary action. Highest tab-stop count in the product (201).
2. **Duplication between the two shared macros.** Five `device_actions` capabilities (Open SSH
   Console, Copy SSH Command, Configuration, Investigate, Predict) are *already* items inside
   `entity_menu`. On `device.html:23-24` both macros render on the same line, so those five
   actions appear twice within a few pixels.
3. **Two opposite mutation models for the same conceptual work.** Policy rows carry **zero**
   per-row mutating forms — assignment is bulk-only, with a select-all and **no selection count
   rendered anywhere**. Changes rows carry **four** POST forms with three inline text inputs and
   **no bulk selection at all**, so *"assign these five changes"* costs ~15 interactions.
4. **Row menus are clipped by their own scroll container.** `.table-scroll` sets
   `overflow-x: auto`, which computes `overflow-y: auto`; the absolutely-positioned
   `.action-menu-list` is therefore clipped. A last-row menu overflows **570 px below** the
   container at 1440 px and is still clipped at 1920 px. **At 375 px it opens at x = 785–1015 —
   entirely outside the viewport.**
5. **The ARIA pattern is half-declared.** The trigger carries `role="button"` +
   `aria-haspopup="menu"` but no `aria-expanded`, and the list is a plain `<ul>` with no
   `role="menu"`/`menuitem`. The `role="button"` override *discards* the expanded/collapsed
   state native `<details>` announces for free. No arrow-key navigation.
6. **DOM weight is real even where tab stops are not.** Policy renders 500–550 menu `<li>`
   items that are never seen; Changes renders 600 hidden inputs per page.

### One correction to my own first reading

I initially inferred that Policy's 292 px action column forced its horizontal scroll. Testing
it: the column's *content* is 176 px, and hiding the column entirely reclaims **11 px**. The
scroll is caused by `.table-scroll-wide`'s hard-coded `min-width: 1080px` overshooting a 1069 px
content column by 11 px — at **every** desktop width, 1440 and 1920 alike. That is a
pre-existing one-line CSS defect unrelated to row actions, recorded in §21 and **not** absorbed
into this PR.

enforced, Escape closes, focus remains on the trigger, outside click closes, `js-copy-link`
copies an absolute URL.

**Blast radius:** 58 occurrences of the row-action patterns across 32 templates.

## 6. Action taxonomy (derived from the real inventory)

| Class | Rule | Real members |
|---|---|---|
| **A — Primary row navigation** | Stays a visible link in its own cell, one per row | Open verdict · Evidence · Open configuration · Open record |
| **B — Secondary navigation** | Inside the overflow menu | Details · Focus in topology · Policy verdicts · Investigate · Predict · Add to Compass · Configuration/Evidence cross-links |
| **C — Mutating workflow** | Overflow menu (single row) **and** bulk bar (many rows); always POST + CSRF + `next` | Acknowledge · Assign · Note · Suppress (+ inverses) |
| **D — Export/copy** | Bulk bar for many; menu for one | Bulk export · Copy SSH command · Copy link |
| **E — Destructive/high-consequence** | Separated at the menu foot; keeps its confirmation | Suppress (requires a reason) · archive/move-aside on storage |
| **F — Developer/internal** | None found in table rows | — |
| **G — Duplicate** | Remove from the row; name the survivor | The five `device_actions` capabilities that `entity_menu` already carries |

---

## 7. Direct-visible vs overflow: **Option B**, uniformly

One visible primary navigation link per row (class A) **plus** one overflow trigger (classes
B–E). Rejected: Option A (no visible action — the row's main purpose deserves a target), Option
C (focus/selection-only reveal — fails touch and discoverability), and whole-row click (conflicts
with text selection, the checkbox, and the cell links; the row is already clickable for
*selection* on selection tables, and overloading that click would be ambiguous).

Concretely: **Evidence and Configuration stop rendering `device_actions` inline in table rows**
and adopt `entity_menu`, whose menu already contains SSH, Copy SSH, Configuration, Investigate
and Predict. `device_actions`' only unique capability — **web management** (Open HTTPS / Copy
HTTPS URL / Open HTTP–Insecure / Copy HTTP URL / the greyed "Web unavailable") — is added to
`ACTION_ORDER` in `linking.py` as a `web` group so nothing is lost. `device_actions` remains
unchanged on **detail pages**, where there is one device rather than fifty.

---

## 8–9. Bulk relationship and the selection decision

**Checkboxes stay permanently visible.** No selection mode. Enterprise operators multi-select
rapidly; the engine already supports select-all with an indeterminate state, and the checkbox
costs 1 tab stop against 4 for the inline buttons it replaces. Introducing a mode would add a
click to every bulk task to save one column.

**Render the bulk bar that the JS already supports**: add `[data-selection-count]` (with
`aria-live="polite"`, exactly as `storage.html:75` does) beside each bulk submit, so selection
finally reports itself. **Give /changes a selection column and a bulk bar** for
acknowledge/assign/suppress — that is the one measured 15-interaction task in the product.

Class-C actions then live in **both** places, which is correct and not duplication: the row menu
acts on one row in context; the bar acts on a set. The rule that prevents competing controls is
that the bar appears only when the selection is non-empty (the count element is empty otherwise,
which is already the JS behaviour).

Semantics to preserve exactly: ids come from the **current page's** checkboxes; `/policy/assign`
requires both an owner and ≥1 subject and flashes otherwise; bulk-export caps at 200 devices and
resolution-centre at 100; every bulk POST keeps CSRF and its `next` redirect; one correlation id
per batch; selection is **not** carried across filter/sort/pagination (a new page renders new
checkboxes, unchecked — the correct default).

## 10. Shared component architecture — **Option C, then B**

The smallest thing that works, in two moves:

1. **A behaviour/CSS layer fix, no template churn** — the menu list escapes its scroll
   container, the ARIA is made honest, arrow keys are added. This fixes every one of the 8
   `entity_menu` call sites at once.
2. **`entity_menu` gains one optional parameter for form actions** so `changes.html` can stop
   hand-rolling: an action may carry `method="post"`, `action=<url>`, `fields={...}`, and an
   optional `input` spec (name/placeholder/required). The macro renders it as a `<form>` inside
   the `<li>`, with `csrf_field()` and the hidden `next`, exactly as changes.html does today.

No action DSL beyond the fields the real call sites already use: `key, label, href, available,
reason, external, method, action, fields, input, group, destructive`. The first six exist today
in `EntityAction`.

## 11–13. GET/POST, permissions, destructive actions

**GET stays GET, POST stays POST.** Every mutating item renders a real `<form method="post">`
with `csrf_field()` and the hidden `next` that returns the operator to their filtered page.
Nothing becomes a link; nothing becomes client-only.

**Permissions**: the macro renders what it is given; the *builder* decides. `device_menu()`
already receives request context, so permission filtering belongs there — not in the template
and never as the authorization boundary. Server-side authorization is unchanged. Following
PR-178's precedent, an action the principal cannot perform is **omitted**, not rendered dead.

**"Not authorized" ≠ "not applicable."** Not-applicable keeps today's excellent treatment — a
greyed item with its reason. One defect to fix while there: `device_entity_actions` accepts
`has_evidence`/`has_configuration` but **no caller passes them**, so the menu can state "no
evidence records are stored for X in this scope" without having checked. Either pass the real
flags or soften the wording.

**Destructive**: Suppress is the only row-level high-consequence action and it already requires
a typed reason. It renders last, after a separator, and keeps its required input. No new
confirmations are added to harmless actions.

---

## 14–16. Keyboard, screen-reader and focus models

**Keyboard**: Tab reaches the trigger (1 stop per row). Enter/Space opens. **Arrow keys move
between items** (new). Escape closes and returns focus to the trigger (already correct). Tab
from an open menu moves to the next row's trigger. Nothing requires a mouse.

**Screen readers**: keep the existing row-aware name (`aria-label="Device for ahmedabad-regional-client"`)
— it is already the recommended pattern. **Drop `role="button"`** so the native disclosure
announces expanded/collapsed, or add `aria-expanded` + `role="menu"`/`menuitem`; the former is
one deletion and restores correct semantics for free. Item labels already name their object
("Evidence for X"); they are verbose but unambiguous, and shortening them would break the
one-item-out-of-context case — keep them.

**Focus**: on open → trigger retains focus (arrow enters the list); on Escape/outside click →
trigger; after a mutating POST → the page re-renders at the same filter/page via `next`, and the
row keeps its id anchor. On bulk completion → the bulk bar's status region. Never the top of the
page.

---

## 17. Responsive

At 375 px the table scrolls **inside** `.table-scroll` (page overflow stays zero — the PR-178
strength, preserved). The trigger is already a 44 px touch target at mobile. The menu must open
**within the viewport**: anchoring it to the right edge of the trigger and allowing it to flip
upward near the bottom, escaping the scroll container. Tables are **not** converted to cards —
no evidence supports that, and it would break column presets and selection.

---

## 18–19. DOM, rendering and performance

Hiding items behind CSS would change nothing; they are already behind a closed `<details>`. The
real reduction comes from **not rendering what is duplicated**: retiring inline `device_actions`
from Evidence/Configuration rows removes 100–150 controls per page and drops Evidence from 201
to ~101 tab stops. Rendering the Changes menu body **on demand** (a `<template>` cloned on first
open, or the same markup emitted only for the open row) removes 600 hidden inputs per page.

**No new per-row backend work.** Eligibility already comes from the request-cached target tuple.
Two pre-existing costs are worth noting and are *not* introduced here: `device_menu()`/
`device_target()` do an O(N) scan per call (O(50·N) per table), and `_web_access_for_request`
re-reads `management-services.json` once per device. Moving web actions into the menu must reuse
the existing per-request cache, not add a lookup. PR-176 budgets are unaffected.

## 21. Risks

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| R1 | Escaping the scroll container breaks table scrolling or z-order | High | Fix positioning without removing `overflow-x`; test at all four widths on the last row |

## 27. Success criteria

Rows read as data with one obvious way in; no row carries a primary-coloured button; every

## 28. Approved implementation plan

**Step 1 — Behaviour and ARIA, no template churn.** Fix the clipping and viewport-fit; add
arrow-key navigation; make the ARIA honest (drop `role="button"`, or complete the menu pattern).
Land the menu tests. All 8 call sites benefit; nothing else moves. *This is the functional bug
fix and it ships even if the rest slips.*

**Step 2 — Remove the duplication.** Add the `web` action group to `linking.py` reusing the
existing per-request cache; switch Evidence and Configuration **rows** from `device_actions` to
`entity_menu`; delete the two dead imports. Measure tab stops before/after.

**Step 3 — Form actions in the shared macro.** Extend `entity_menu` minimally; migrate
`changes.html` onto it, preserving all four POSTs, CSRF, `next`, inputs and eligibility branches
byte-for-byte in behaviour.

**Step 4 — Selection and bulk.** Render `[data-selection-count]` beside existing bulk submits;
add selection + a bulk bar to Changes for acknowledge/assign/suppress, reusing
`/changes/annotate` semantics; update the SELECTION_TABLES registry deliberately.

**Step 5 — On-demand menu DOM**, only if Step 2's measurement shows the remaining DOM weight
matters; server-rendered closed markup stays the no-JS baseline.

**Step 6 — Validate**: full suite, four widths, three roles, the eight operator tasks, and a
PR-176 performance recheck.

**Handover must state:** before/after counts per page; that every §20 action remains reachable;
that no POST became a GET; the measured keyboard and DOM reduction; and whether Step 5 was needed
or skipped.
