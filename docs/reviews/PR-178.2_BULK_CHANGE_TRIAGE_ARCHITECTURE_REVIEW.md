# PR-178.2 — Bulk Change Triage

**One Operational Decision. Many Changes.**
*Audit + domain semantics + architecture. No code was modified. Nothing was committed.*

Traced against HEAD `6388dff` (post-PR-178.1), measured against the running application,
a purpose-built two-scope workspace, and the real browser engine.

---

## 1. Executive diagnosis

The brief's first principle is correct, and the repository proves it harder than expected.
`for subject in subjects: call_existing_route(subject)` is unsafe here for **four measured
reasons**, not one:

1. **It is 80× slower than it needs to be.** Every `AnnotationStore.set()` rewrites
   `annotations.json` *and* rewrites the whole append-only `audit.jsonl`. Measured: 50 subjects
   cost **1,065 ms** on an empty audit log and **2,032 ms** at 10,000 audit lines, growing with
   the log. One batched write of the same 50 costs **13 ms / 31 ms**.
2. **It would abort halfway on a mixed selection.** `store.clear()` *raises* when the subject is
   not in that state (measured: `"no change-ack annotation exists for change:…"`). A naive loop
   stops at the first already-unacknowledged row and leaves the rest untouched, with one error
   flash and no account of what did happen.
3. **It cannot be correlated.** `AnnotationStore.set()` accepts `correlation_id`;
   **`clear()` does not** — so bulk unacknowledge/unsuppress cannot join the batch that the audit
   model already promises.
4. **It would flood the operator chronology.** Every audit event becomes exactly one Timeline
   row (`chronicle.py:195-218`), and annotation events are not `system`-flagged, so they land in
   the default operator view. One "acknowledge 50" becomes 50 near-identical Timeline rows.

Two further facts change the shape of the answer:

- **Change identity is content-addressed and scope-independent.**
  `change_fingerprint` hashes `(kind, category, device, field, before, after, description)` —
  **not** network, run, or timestamp. Measured on real `unified_rows` output: the same change
  observed in Hyderabad and Secunderabad produces the **identical** subject, and acknowledging it
  in one scope marks it acknowledged in the other. This is deliberate durability (an
  acknowledgement survives re-discovery) with an undeclared side effect (it crosses scopes).
- **The browser forbids the obvious form architecture.** Measured in the real engine: a checkbox
  belongs to **exactly one** form, so per-action endpoints cannot share one selection; and a
  single `required` field in a shared bulk form **blocks every submit button in it**, including
  the actions that need no input.

The good news: Atlas already owns almost all the machinery. `AuditEvent` documents the exact
model this PR needs — *"a bulk action emits one event per subject under one correlation id"* —
and carries an `outcome` field (`success | denied | conflict | failed`). `incidents_bulk` already
implements eligible-subset with honest skip reporting. `evidence_bulk_export` already dedupes and
caps. PR-178.1 already shipped the selection engine, the counted bulk bar, and the permission
gate. **This PR is mostly assembly plus one new service — not new infrastructure.**

**Six defects found in the traced path** (all pre-existing; §28 places each):

- **D1 — no subject validation.** Measured: posting `subject=change:deadbeefdeadbeefdead` (never
  rendered anywhere) returns success and writes a durable orphan annotation.
- **D2 — cross-scope annotation leakage.** Measured (§3).
- **D3 — dead UI for 5 of 7 roles.** `changes.html` contains no `can(...)` call, yet
  `changes.annotate` is granted only to **investigator** and **system-admin**. Viewer,
  network-operator, policy-manager, credential-admin and approver all see a full "Act" menu whose
  every form 403s. (`network-operator` — the most likely triage role — is among them.)
- **D4 — audit events lose their scope.** `AnnotationStore.set/clear` never pass `scope_id`, so
  every annotation audit event records `scope_id="all"` regardless of where it happened.
- **D5 — `clear()` cannot be correlated** (no `correlation_id` parameter).
- **D6 — notes overwrite silently.** `set("change-note")` replaces the previous note with no
  before/after shown to the operator (the audit does keep `before`).

## 3. Change identity model

```
subject = "change:" + sha256("kind|category|device|field|before|after|description")[:20]
```

| Question | Answer (measured) |
|---|---|
| Includes scope/network? | **No** — `change_fingerprint` ignores the `network` key that `finish()` sets |
| Includes run id / timestamp? | **No** |
| Same change, two scopes? | **Identical subject.** Hyderabad and Secunderabad both render `change:db289b12d3e9478b2719`; acknowledging in Hyderabad shows "acknowledged" in Secunderabad |
| Same change, later run? | **Identical subject** — this is the durability the design intends |
| Recurring but *different* change (2→3 then 3→4)? | **Different subject** — a new delta is never silently pre-acknowledged |
| Can a subject vanish between GET and POST? | **Yes** — measured: after a new report the old subject no longer renders; its annotation persists as an orphan |
| Can a subject be re-pointed at a *different* logical change? | **No.** Content-addressing means a changed change has a changed id. This is the strongest property in the model and it is what makes an optimistic-concurrency token unnecessary. |

**Consequence for this PR:** the only honest staleness rule is *"a subject that does not appear in
the current scope's rows is not mutated, and is reported as no longer present"* — which is
simultaneously the stale-subject rule and the anti-tampering rule.

## 4. Bulk-action eligibility matrix

| Action | Bulk? | Required input | Reversible | State compared to decide UNCHANGED | Consequence |
|---|---|---|---|---|---|
| **Acknowledge** | **Yes** | none | yes (unacknowledge) | presence of `change-ack` | low |
| **Unacknowledge** | **Yes** | none | yes | absence of `change-ack` | low |
| **Assign** | **Yes** | `owner` | yes (re-assign) | stored `owner` **equals** the requested owner | medium — replaces another owner |
| **Suppress** | **Yes** | `reason` | yes (unsuppress) | stored `reason` **equals** the requested reason | **high** — hides rows by default |
| **Unsuppress** | **Yes** | none | yes | absence of `change-suppression` | medium |
| **Note** | **NO** | `note` | **no** | — | **destructive** |

**Note is deliberately excluded.** Three independent reasons: (a) the store keeps **one** note per
subject and `set()` **overwrites** it, so one bulk note would silently destroy N operator-written
notes with no undo path; (b) the data model has no batch-note entity, so "one note referenced by N
subjects" would be a new schema this PR should not invent; (c) a note is per-change commentary —
identical text on eight different changes is not one decision, it is eight unwritten notes. Bulk
note stays out; the per-row note form is untouched.

**"Already in state" is per-action, not per-key** — the adversarial pass amended this (§31.1):
re-suppressing with a *different* reason and re-assigning to a *different* owner **are** mutations
and must be reported as such.

## 5. Selection architecture

| Question | Decision |
|---|---|
| Checkboxes visible? | **Permanently visible**, no selection mode — PR-178.1's decision, unchanged |
| Gated? | **Yes — `can('changes.annotate')`**, exactly the Policy `can('policy.manage')` precedent PR-178.1 established. 5 of 7 roles get no selection column, and (D3) no dead row menu either |
| Row with only some actions applicable? | The row is still selectable. Applicability is a *server-side outcome*, reported per subject — never a disabled checkbox that leaves the operator guessing |
| Select-all scope | **This page only** (§6) |
| Survives pagination? | **No** — a new page renders new, unchecked boxes |
| Survives filter/sort? | **No** — same reason, and the correct default |
| Survives browser Back? | **Yes**, and PR-178.1's `pageshow` re-sync already keeps the count, row outlines and bar honest |
| Survives a new discovery? | **No** — and it must not: the subjects would be stale, and the server rejects any that no longer render |
| Cross-page selection? | **Rejected.** No operational value that justifies mutating rows the operator never saw |

The engine needs **no changes**: `data-row-select="subjects"` on the table, `data-select-all` in
the header, `[data-selection-count]` and `data-bulk-bar` on the bar. Measured in the browser: the
engine finds checkboxes that are `form=`-associated to an external form, and its
`table.closest("form") || document` count lookup resolves correctly when the table has no form
ancestor.

## 6. Select-all semantics

**Select all = every row on this page, and it says so.**

The page already renders `312 change(s) match — showing 1–50`. The select-all control is labelled
`"Select all 50 changes on this page"` and the count reads `"50 of 50 on this page selected"`.

Options B (all filter matches) and C (all in scope) are **rejected**: with `per_page` capped at
200 and 312 matches, either would mutate up to 262 rows the operator never saw, and neither can be
previewed honestly on the confirm page. If a "select every match" workflow is ever wanted it needs
its own design (a server-side filter-scoped operation with its own preview), not a checkbox.

## 7. Bulk action UX

Two shapes, chosen by whether the action needs input — and that split is forced by a measured
browser constraint (§9), not by taste.

**The contextual bar** (PR-178.1's `data-bulk-bar`, hidden while the selection is empty):

```
  12 of 50 on this page selected                     [Clear selection]
  [Acknowledge]  [Unacknowledge]  [Assign…]  [Suppress…]  [Unsuppress]
```

- Ordering: reversible/low-consequence first; the ellipsis marks "one more step".
- **No action is a primary button.** `Suppress…` is separated at the end and carries the
  destructive treatment; nothing here competes with the page's own primary action.
- Mixed-eligibility guidance is **not** guessed in the browser. It is computed by the server and
  shown either on the confirm page (input actions) or in the result (direct actions).

**The confirm page** — `Assign…` / `Suppress…` POST the selection and render (200, no mutation):

```
  Suppress 12 changes
  10 will be suppressed · 2 are already suppressed with a different reason and will be updated
  Reason (required) [___________________]
  [Suppress 12 changes]   [Cancel — back to your filtered view]
```

It is a **server-rendered page**, not a modal: no modal infrastructure is introduced. It doubles
as the preview the brief asks about — earned by necessity rather than an invented
"more than 10" rule. Acknowledge / Unacknowledge / Unsuppress need no input and submit directly.

## 8. Endpoint architecture

**One endpoint: `POST /changes/bulk`**, discriminated by the submit button
(`name="bulk_action"`, value in `acknowledge | unacknowledge | assign | suppress | unsuppress`).

This is not a preference — it is forced. **Measured: a checkbox can be associated with exactly one
form.** With separate `/changes/bulk/acknowledge`, `/changes/bulk/suppress`… endpoints, each
action's form would need its **own** copy of all 50 checkboxes. One form, one endpoint, an
explicit server-side action allowlist.

| Criterion | How the single endpoint answers |
|---|---|
| Validation clarity | One `BULK_ACTIONS` table: required fields, annotation kind, comparison rule |
| Authorization | One `ENDPOINT_PERMISSIONS` entry (`changes_bulk: CHANGES_ANNOTATE`) — and an unmapped endpoint fails closed, pinned by an existing test |
| Cross-action inputs | The endpoint reads **only** the fields its action declares; `owner` is ignored by suppress and vice versa |
| Extensibility | A new bulk action is one table row plus one button |

`GET` is never used to mutate. The confirm render is a POST that mutates nothing.

## 9. Form architecture

**Proven in the real browser engine, on a real Atlas page:**

```
nested forms .................................. 0
subjects collected by the bulk form ........... only the checked ones
row form field set ............................ {subject, action} — no bulk fields
bulk form field set ........................... {_csrf, next, subjects, …} — no row fields
association when the form is declared AFTER the checkboxes ......... works
a checkbox bound to a second form ............. collects NOTHING (single-form only)
a required field in the shared form ........... blocks EVERY submit button
formnovalidate on a button .................... bypasses it for that button only
```

```html
{# filters close here — verified: changes.html filter forms end before the table #}
<div class="table-scroll"><table data-row-select="subjects">
  …<td><input type="checkbox" form="changes-bulk" name="subjects" value="{{ change.subject }}"></td>
  …<td class="row-actions">  {# the four per-row POST forms, untouched #}
</table></div>

<form id="changes-bulk" method="post" action="/changes/bulk" data-bulk-bar>
  {{ csrf_field() }}<input type="hidden" name="next" value="{{ request.full_path }}">
  <span data-selection-count aria-live="polite"></span>
  <button type="submit" name="bulk_action" value="acknowledge">Acknowledge</button>
  …
</form>
```

The bulk form is a **sibling** of the table — never a wrapper. **No nested form exists anywhere in
the design**, and a test must fail if one appears.

**Native validation lives on the confirm page, not in the bar.** The bar cannot carry
`required` (it would block sibling actions — measured); the confirm page renders exactly one
action's field and marks it `required` natively. The server validates in both cases and is the
authority. This is the honest reading of "native validation where possible".

## 10. Authorization model

- **One capability governs all bulk change actions: `changes.annotate`** — verified at HEAD, not
  assumed. Granted to `investigator` and `system-admin` only.
- The permission is enforced in `before_request` from `ENDPOINT_PERMISSIONS`; a denial is audited
  with actor, roles, endpoint and `outcome="denied"`. Authorization is **whole-request** — it can
  never be partial across subjects, which removes a whole class of ambiguity.
- Authorization changing between GET and POST resolves correctly: the POST is evaluated against
  current permissions and denied wholesale.
- **UI gating is not authorization**: the selection column, the bar, *and* (D3) the row menu are
  gated on the same capability purely so no principal is offered a control that will 403.
- Scope is a **view filter, not a permission boundary** in Atlas — so validating subjects against
  the scope carried in `next` is anti-tampering, not access control, and cannot be used to
  escalate.

| Field | Rule | Source |
|---|---|---|
| `bulk_action` | must be in the allowlist | new, mirrors the existing action allowlist |
| `subjects` | ≥1 after dedupe; **each must appear in the current scope's rendered rows** | new (fixes D1 for the bulk path) |

## 12. Mixed-eligibility semantics

**Model: ELIGIBLE-SUBSET with per-subject outcomes** — the same model `incidents_bulk` already
uses, and the only one that satisfies "do not call already-acknowledged a failure".

Rejected: *strict atomic* (one already-acknowledged row would refuse the other nine — hostile);
*best effort without reporting* (hides truth); *transactional rollback* (the stores have no
cross-file transaction, and pretending otherwise would be the dishonesty this PR exists to
prevent).

Per subject, deterministically:

| Outcome | Meaning | Mutation | Audit |
|---|---|---|---|
| `UPDATED` | state actually changed | yes | 1 event, `outcome="success"`, batch correlation |
| `UNCHANGED` | already exactly in the requested state | **no** | **none** — a no-op is not a mutation |
| `NOT_PRESENT` | subject does not appear in this scope's rows | no | none (the batch record notes the count) |
| `FAILED` | persistence refused | no | 1 event, `outcome="failed"` |

The **UNCHANGED comparison is per action** (adversarial amendment §31.1): acknowledge compares
presence; assign compares the stored **owner**; suppress compares the stored **reason**. Assigning
an already-owned change to a *different* owner is `UPDATED` (a replacement), and the confirm page
says so before it happens.

*Deliberate divergence, recorded:* the single-row route re-writes and re-audits an identical
acknowledge (measured: +2 audit lines for 2 identical acks). The bulk path writes nothing for
`UNCHANGED`. Single-row behaviour is **not** changed by this PR.

## 13. Partial-failure semantics

The result is a sentence with four counts, and never a bare "Success":

> **12 changes · 9 suppressed · 2 already suppressed with this reason · 1 no longer present.**
> [Review this batch]

- Categories exist only where the domain supports them (§12). "Already in state" is never called a
  failure.
- `[Review this batch]` links to `/changes?...&batch=bulk:<hex>` — a new filter, mirroring
  Policy's existing `?assignment=<correlation>`, resolving the batch **server-side from the
  audited annotations**. The redirect carries a short correlation id, never a subject list.
- Zero-effect batches say so plainly: *"No change — all 12 were already acknowledged."*

## 14. Transaction model

**Measured, and the reason the service must exist:**

| 50 subjects | empty audit log | 10,000-line audit log |
|---|---|---|
| Naive loop (`set()` per subject) | 1,065 ms | 2,032 ms |
| **Batched: one annotations write + one audit block** | **13 ms** | **31 ms** |

The guarantee Atlas can actually make, stated exactly:

> **The annotation batch is atomic** — one read-modify-write of `annotations.json` through the
> existing temp-file-plus-atomic-replace, under the existing per-workspace lock. Either all
> `UPDATED` subjects are stored or none are.
> **The audit block is a second atomic write.** On audit failure the service restores the
> in-memory pre-image and reports the batch as failed. A process death *between* the two writes
> can still leave a mutation unaudited — the same exposure the single-row path has today, reduced
> from N windows to one.

This needs two small store additions: `set_many(...)` / `clear_many(...)` on `AnnotationStore`
(batch write, one audit block, shared correlation id) and `append_many(...)` on `AuditLog`.
`clear_many` also fixes **D5** by accepting `correlation_id`. Ordering is mutation-then-audit so
the audit can never claim a change that did not happen.

## 15. Batch / correlation model

One operator intent → one correlation id → N subject-level audit events. **This is not a new
tracing system**: `AuditEvent` already documents exactly this, `policy_assign` and
`incidents_bulk` already mint `f"bulk:{uuid4().hex}"`, and `?assignment=<correlation>` already
proves the read path.

| | |
|---|---|
| Generation | `f"bulk:{uuid4().hex}"`, once per accepted batch |
| Persistence | on every subject's audit event **and** inside each annotation record (`correlation`, `batch_size`) — the `policy_assign` precedent, so a batch stays resolvable after a restart |
| Propagation | the redirect's `?batch=`, the result sentence, the collapsed Timeline row |
| Retry | a re-submit is a **new** batch with a new id; its outcomes will be `UNCHANGED` |

---

## 16. Audit model

**N subject-level events sharing one correlation id.** No batch-level pseudo-event that could
drift from the subject events, and never one collapsed "8 changes modified" record.

Every affected change can be answered from its own event: **who** (`actor` + `actor_roles`),
**what** (`category`, `operation`, `before`/`after`), **when** (`occurred_at`), **why** (`reason`),
**whether it really changed** (`before != after`; `UNCHANGED` writes nothing), and **which batch**
(`correlation_id`).

Two corrections land here: **D4** — the bulk service passes the real `scope_id` (annotation audit
events currently all record `"all"`); and `outcome` is finally used for what it was designed for
(`failed` on a refused subject).

---

## 17. Timeline / chronicle model

Today every audit event becomes one chronicle row, and annotation events are not system-flagged —
so one bulk action would push 50 near-identical rows into the default operator view.

**Decision: collapse by correlation id in the chronicle only.**

> `Ahmed acknowledged 12 changes` · *audit batch bulk:9f3c…* → `/audit?correlation=bulk:9f3c…`

- Events **without** a correlation id (every single-row action) are untouched.
- `/audit` keeps all 12 subject events; the audit page gains a `correlation` filter so the
  drill-down link resolves. Nothing is hidden — one row in the chronology, full detail one click
  away, exactly the separation PR-178 established.

---

## 18. Stale-subject model

**No optimistic-concurrency token and no locking.** Content-addressed identity already provides
the guarantee a token would buy: a change whose content changed has a *different* subject, so a
stale subject can never be applied to a different logical change — it can only fail to resolve.

The rule: **a subject must appear in the rows of the scope carried by `next` at POST time**;
anything else is `NOT_PRESENT` and is reported, never mutated. The confirm page's preview may be
stale by the time it is submitted; the **result**, computed at mutation time, is the truth, and it
is what the operator is shown.

---

## 19. Idempotency / double-submit model

Naturally safe, by measurement and by construction:

- Actions are **state-convergent**: a repeat produces `UNCHANGED` and writes nothing.
- Measured: a repeated single-row acknowledge changes no state (it re-audits; the bulk path will
  not).
- A double-clicked bulk submit creates a second batch whose result honestly reads *"12 unchanged"*.
- Assign's notification is already suppressed when the owner is unchanged.
- **No idempotency token is warranted.** JS may disable the submit while in flight — UX only,
  never a server guarantee.

## 20. Scope / workspace security

| Attack | Defence |
|---|---|
| Forged subject id (**measured to work today**, D1) | must appear in the current scope's rendered rows |
| Subject from another scope | same rule — but see the honest limit below |
| Duplicate ids inflating counts | `dict.fromkeys` dedupe before counting (`evidence_bulk_export` precedent) |
| Thousands of ids | rejected above 200, not truncated |
| Malformed ids | never used as a path or key without matching a rendered row |
| Redirect tampering | `safe_redirect_target` on both POSTs |
| Cross-workspace | the store is constructed from `ATLAS_WORKSPACE_ROOT`; no id can reach another workspace |

**The honest limit, stated plainly:** because the fingerprint is scope-independent (§3), a subject
legitimately visible in one scope *is* the identical change in another, and annotating it there is
existing behaviour — **measured, pre-existing, and not introduced by this PR**. Bulk amplifies it
50×, so the review records it as its own defect (§28 D2) rather than pretending a subject-scope
check fixes it. Fixing it means putting the scope in the fingerprint, which changes single-row
semantics and invalidates stored annotations — a migration, and its own PR.

---

## 21. Return-context model

`next` carries the full filtered URL (`request.full_path`), is validated by `safe_redirect_target`
on both POSTs, and returns the operator to the same scope, filters, sort and page. `Cancel` on the
confirm page returns to the identical URL with the selection intentionally dropped (the honest
default — the page is re-rendered from the server).

**Rows disappearing is expected and must not read as data loss.** Acknowledging under
`status=unacknowledged`, or suppressing at all, removes those rows from the default view. The
result sentence names exactly what happened and survives the redirect; the page already renders
`N suppressed change(s) hidden — tick "show suppressed" to include them`; and
`[Review this batch]` shows precisely the rows that moved.

## 22. Performance model

| Path | Cost | Note |
|---|---|---|
| Bulk write, 50 subjects | **13–31 ms** batched vs 1,065–2,032 ms looped | measured |
| Subject validation | one `_change_rows_for(scope)` per request | the same load the redirect target performs anyway |
| Annotation loads inside that call | **4 full parses** of `annotations.json` (`store.all()` × 4) | small file today (760 B live); easy single-load win, recorded in §28 |
| Report loads | 3 JSON reports per scope, already `load_json` | unchanged |
| PR-176 | untouched — no report regeneration, no enterprise-graph rebuild, no per-subject store construction | |

Shared state is loaded **once per batch**: one row set, one annotations read, one write, one audit
block. Nothing scales with subject count except the in-memory comparison.

## 23. No-JS behaviour

Without JavaScript: checkboxes are real inputs bound by `form=` (association is a parser feature,
not a script feature — measured); the bulk bar is server-rendered and stays visible (PR-178.1's
hide-when-empty is the JS enhancement); submit buttons submit; the confirm page is an ordinary
page with native `required`; CSRF and `next` are hidden fields; the per-row forms are untouched;
and submitting an empty selection produces the honest *"Select at least one change."*

Only **select-all** degrades — it is inherently script-driven, as the engine's own comment already
records. JS never becomes the authorization or correctness layer: every eligibility decision is
made server-side at mutation time.

## 31. Adversarial review findings

Performed against the architecture above, before presenting it. Five findings changed the design;
all amendments are already folded into §1–§30.

**31.1 — BLOCKER (amended): "already in state" was wrong for two of the five actions.**
The first draft treated `UNCHANGED` as "an annotation of this kind exists". Attack: suppress 5
where 2 are already suppressed **for a different reason** — the operator's stated reason would be
silently discarded and the old one kept, while the summary reported "2 already suppressed". Same
for assign: re-assigning an owned change to a *different* owner is precisely the intent, and it
would have been dropped. **Amendment:** the comparison is per action, against the stored value
(§12) — presence for acknowledge, `owner` for assign, `reason` for suppress.

**31.2 — BLOCKER (amended): per-action endpoints are impossible with a shared selection.**
The draft entertained `POST /changes/bulk/<action>`. Measured in the real browser: a checkbox
associates with exactly **one** form, so the second action's form collected **zero** subjects.
**Amendment:** one endpoint, discriminated by the submit button (§8).

**31.3 — BLOCKER (amended): a `required` field in the bulk bar disables every other action.**
Measured: with `required` on the shared reason field, `checkValidity()` fails for the whole form,
so Acknowledge cannot submit either; `formnovalidate` bypasses it per button but then abandons
native validation altogether. **Amendment:** no `required` in the bar; input-taking actions route
through a confirm page that carries exactly one action's field with native `required` (§7, §9).
This also delivered the suppression preview without inventing a threshold rule.

**31.4 — BLOCKER (amended): silent truncation would have shipped the very dishonesty this PR
opposes.** The draft copied `evidence_bulk_export`'s `[:200]`. A 5,000-id POST would report
success for 200 and say nothing about 4,800. **Amendment:** reject over the cap with an explicit
message (§11); the existing silent truncation elsewhere is recorded as D9 rather than propagated.

**31.5 — HIGH (amended): the audit-write window is worse in bulk than single-row.**
Mutation-then-audit leaves an unaudited mutation if the audit write fails — tolerable for one
subject, not for 200 under one operator intent. **Amendment:** the batch service keeps the
pre-image and restores it if the audit block fails, reporting the batch as failed; the residual
(process death between the two atomic writes) is stated in §14 rather than papered over.

**Attacks that did *not* change the design** — recorded so the next reviewer need not re-run them:

- *Stale subjects* — content-addressed identity means a changed change has a changed id, so a
  stale subject can only fail to resolve, never mis-target. No token needed (§18).
- *Scope escape via a crafted `next`* — `_scope_from_next` already validates against known scopes
  and falls back to Enterprise, and scope is not a permission boundary, so the widest reachable row
  set is the one the principal may already view (§20).
- *Double submit* — state-convergent actions make the second batch all-`UNCHANGED` (§19).
- *Timeline flooding* — collapsing only correlated events leaves every single-row event untouched
  (§17).
- *Authorization change between GET and POST* — whole-request evaluation denies wholesale (§10).
- *No-JS* — `form=` association is a parser feature; only select-all degrades (§23).
- *Nested forms* — measured zero in the proposed markup, in both document orders (§9).
- *Performance* — the batched write is 80× the loop and the validation pass is work the redirect
  target repeats anyway (§22).

**One finding I could not fully resolve, stated rather than buried:** cross-scope annotation
leakage (D2) is real, measured, pre-existing, and **amplified** by bulk. The architecture confines
the *new* surface (subjects must render in the current scope) but cannot repair the identity model
without a migration. If that is unacceptable for beta, D2 must be scheduled **before** this PR,
not after — that is a product call, and it is flagged here rather than discovered later.

## 35. Success criteria

For **every** affected change, from its own audit event: who acted, what action, when, why,
whether it actually changed, whether it was already in that state, whether it was skipped and why,
whether it failed, and which batch it belonged to. The operator sees one honest sentence with four
counts and can open the exact batch. `7 succeeded / 2 unchanged / 1 failed` is never rendered as
`10 succeeded`. Single-row workflows are byte-identical. No nested form exists. 50 subjects
complete in tens of milliseconds, not seconds. And no principal is offered a control that will
