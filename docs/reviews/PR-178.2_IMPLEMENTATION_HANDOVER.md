# PR-178.2 — Implementation Handover

**Bulk Change Triage — One Operational Decision. Many Changes.**

Implemented per the approved PR-178.2 architecture (with its five adversarial amendments),
on top of the PR-178.2A scoped-identity foundation. Validated against the full suite, a
password-mode two-profile world driven through the real browser as three roles, and
adversarial requests fired at the live endpoint.

---

## 1. Executive result

An operator can now say "these twelve changes are one decision" and Atlas executes it as one
batch — while still answering, for every affected change: who acted, what happened, when, why,
whether it actually changed, whether it was already in that state, whether it was skipped, and
which batch it belonged to. `7 updated / 2 unchanged / 1 not-present` is never rendered as
`10 succeeded`. A 50-subject batch is one annotation write and one audit block instead of 100
full-file rewrites. Five roles that used to be offered an Act menu that could only 403 now get
readable data with zero dead controls. Single-row workflows are untouched — and the single-row
route inherited the bulk path's forged-subject validation, closing the last measured orphan-write
defect.

## 4. Batch service architecture

`change/bulk.py` is pure domain logic (no Flask, no I/O): `BULK_ACTIONS` (kind, required input,
clear-shadow), `classify()` → a `BatchPlan` of per-subject `PlanEntry`s, `execute()` → at most two
annotation writes (a clear block and/or a set block) plus their audit blocks through the new store
primitives, `summary_sentence()` → the honest four-count sentence. The route owns request
concerns only: authorization (middleware), CSRF (middleware), `next` validation, subject-set
construction, confirm-page flow, flash and redirect.

## 5. Supported bulk actions

Acknowledge · Unacknowledge · Assign (owner required) · Suppress (reason required) · Unsuppress.

## 6. Bulk Note is excluded — deliberately

The store keeps ONE note per subject and `set()` **overwrites** it: one bulk note would silently
destroy up to 200 operator-written notes with no undo path, and "the same text on twelve
different changes" is twelve unwritten notes, not one decision. The single-row Note form is
untouched (pinned: the bulk bar offers no note action; the row form still posts one).

## 7. Subject / scope validation

Every posted subject must appear in `_valid_change_subjects(next)` — the rows the operator's
working context currently renders (scope resolved by the existing validated `next` machinery),
plus, when `next` is a run comparison, that comparison's reconstructed rows (annotating from the
comparison view is an existing workflow and survives). Parsing the v2 subject is never trusted on
its own: **browser-fired proof** — a forged same-scope subject and a *real* subject stolen from
Secunderabad both came back `1 change(s) · 1 no longer present in this view.` with zero mutation.
Oversized batches (201+) are rejected with "Nothing was changed", never truncated; duplicates
count once (`dict.fromkeys` order).

## 8. Single-row forged-subject convergence

`/changes/annotate` now applies the same existence check before touching any store. Measured
before: a forged subject wrote a durable orphan annotation. Now: *"That change is not part of
this view any more — nothing was modified."* Real single-row workflows (including Note, and
annotating from a comparison) are pinned unchanged; the RBAC status behaviour of the route is
unchanged (302 either way).

## 9. Form architecture — no nested forms

The bulk form is a **sibling** rendered *after* the table, and row checkboxes join it via
`form="changes-bulk"` — the per-row POST forms inside the table stay valid. Pinned by a
form-nesting depth scan of the rendered page (max depth 1) plus explicit position and association
assertions; verified again in the live browser (`checkbox.form.id === "changes-bulk"`).

## 10–11. Selection & select-all semantics

Page-local, dataset-local; nothing survives pagination, filter, sort or scope changes; browser
Back re-syncs through PR-178.1's `pageshow` hook. Select-all is **this page only** and says so:
`"Select all 14 changes on this page"`, count `"12 of 14 on this page selected"` (live-measured) —
via a new opt-in `data-selection-phrase` attribute so other selection pages keep their existing
wording. Row checkboxes carry identifying names (`"Select the high topology change on R-h00"`).
Clear selection unchecks through the engine's own code path.

## 12. Authorization behaviour by role (browser-verified, password mode)

| Role | /changes |
|---|---|
| viewer (vera) | data readable · no checkboxes · no Act menu · no bulk form |
| network-operator (oper) | identical — **no dead controls that 403** (the D3 fix); permissions deliberately NOT widened |
| investigator (ivy) | checkboxes, select-all, Act menu, bulk bar, and the endpoint accepts her batch |

`changes_bulk → changes.annotate` in the authz map (bulk is a quantity, not a new privilege),
enforced by the fail-closed middleware; the RBAC matrix row pins investigator+admin allowed,
five roles denied. Authorization is whole-request: a mid-flight permission change denies the
POST wholesale.

## 13. Confirm-page behaviour

Assign… and Suppress… POST once, mutate nothing, and render an ordinary server page (no modal
framework) with: the eligibility breakdown ("3 are unassigned · 2 already have an owner —
**replaced** otherwise" / "12 will be newly suppressed… reversible"), the one natively-`required`
field (with `autofocus`), the selection as hidden inputs, and Cancel back to the exact filtered
view. A confirmed submission missing its input re-renders with the error and the selection
intact. The preview classifies against a sentinel no real value can equal, so it never guesses
what the operator will type; **the confirmed submission re-classifies and that result is the
truth** (staleness rule).

## 14–15. Mixed eligibility & per-action UNCHANGED semantics

`UPDATED / UNCHANGED / NOT_PRESENT` per subject (eligible-subset model). The comparisons are
per action, per the adversarial amendment: assign compares the stored **owner** (a different
owner is a real replacement — browser-verified: sara's two rows moved to ahmed and the confirm
page said so beforehand); suppress compares the stored **reason** (a different reason updates the
record — pinned); acknowledge/unacknowledge/unsuppress compare effective presence, with scoped
negatives honoured. Un-acting on legacy-asserted state writes a **scoped negative shadow**, never
touching the read-only pre-isolation record (pinned end-to-end through the endpoint).

## 16. Transaction / failure guarantee

Exactly the approved contract: the annotation batch is one atomic temp-file replace; the audit
block is a second atomic write; if the audit block fails the store restores the annotation
pre-image and the route reports *"The bulk action failed and nothing was changed."* (failure
injection pinned). **Stated residual:** a process death *between* the two atomic writes can still
leave an unaudited mutation — the single-row path's pre-existing exposure, reduced from N windows
to one. No stronger atomicity is claimed.

## 17–18. Audit & correlation model

One audit event per **UPDATED** subject — never for UNCHANGED (a no-op is not a mutation), never
for NOT_PRESENT — all sharing one `bulk:<uuid>` correlation id, each carrying the real actor,
`actor_roles`, the subject's own `scope_id`, before/after, reason and timestamp. Server-verified
after the browser session: three batches, exactly 5 + 5 + 12 events. The correlation id lives in
the URL as a short token; subjects are never carried in a query string — the batch view resolves
them server-side **from the audit log**, which stays correct for clear-type actions too.

## 19–20. Timeline collapse & /audit correlation filter

Audit events sharing a `bulk:` correlation collapse to ONE operator chronology row — live:
`ivy acknowledged 5 change(s)`, `ivy assigned to ahmed 5 change(s)`,
`ivy suppressed 12 change(s)`; exactly 3 batch rows, zero per-subject rows — each linking to
`/audit?correlation=<id>`, where all N subject events remain (live-verified: 12/12). Uncorrelated
single-row events keep one chronology row each (pinned). Nothing historical was rewritten;
`policy_assign`'s existing bulk batches gain the same collapse, consistent with "one intent, one
row".

## 21. Worked mixed-result example (from the live browser session)

Selected 3 where 1 was already acknowledged and 1 was forged:
**`3 change(s) · 1 acknowledged · 1 already acknowledged · 1 no longer present in this view.`**
Zero-effect: **`No change — all 2 selected change(s) were already acknowledged.`** (with no new
audit events — pinned).

## 22. Rows disappearing after mutation

Suppressing 12 under the default filter leaves 2 visible rows and the honest note
`12 suppressed change(s) hidden…`; the flash sentence survives the redirect; **Review this batch**
opens `/changes?batch=<id>` showing exactly the 12 — suppressed included, because a suppression
batch IS suppressed rows (live-verified: 12/12 rows, banner, audit link).

## 23. Double submit

State-convergent, no idempotency token: the second submit classifies everything UNCHANGED,
mutates nothing, writes no audit events (pinned with audit-line counts). The residual `batch_done`
wart this exposed (`c830e07`) is fixed: consecutive batches never link the wrong review.

## 24. No-JS behaviour

Checkboxes are real inputs bound by `form=` (a parser feature, proven in PR-178.2's architecture
probes); the bulk bar is server-rendered visible (hide-on-empty is JS-only); direct actions
submit; Assign/Suppress land on ordinary confirm pages with native `required`; CSRF and `next`
are hidden fields; per-row forms untouched. Only select-all degrades (inherently JS). Validated
via markup and endpoint tests — the pane cannot disable JS (stated limitation, as in prior PRs).

## 25. Accessibility validation

Identifying checkbox names; select-all names the page count; the bulk form is
`role="group"` + `aria-label="Bulk actions for the selected changes"`; the count is the existing
`aria-live="polite"` region; selection never steals focus; the confirm field carries `autofocus`
(the attribute is the mechanism — the pane doesn't grant tab focus, so `document.activeElement`
could not be asserted there); errors re-render with the field focused and selection intact;
Suppress is separated with the one high-consequence treatment and is never a primary button.
Keyboard-only end-to-end rests on ordinary form controls in document order (no pointer-only
step exists); the pane cannot synthesize trusted key events (stated limitation).

## 27. Performance

Write-amplification pinned at the endpoint: a 50-subject batch = **1 annotation write + 1 audit
block of 50 events** (the architecture measured the naive loop at 1,065–2,032 ms and 100 file
rewrites for the same work; the guard is write-counts, not wall-clock, so CI stays stable).
Shared state is loaded once per batch (one row set, one annotations read). The batch review view
costs one audit scan only when `?batch=` is actually used. PR-176 / PR-178.1 budgets untouched.

## 30. Deviations from the approved architecture

1. **Steps 2–4 in one commit** (§2) — shared files; every commit stays green.
2. **Review affordance instead of auto-entering the batch view**: the architecture's §13 and §21
   pulled in different directions (redirect carries the id vs. return to exact context). Resolved
   following the `policy_assign` precedent: return to the operator's exact context, with the flash
   sentence plus a one-click *Review this batch* banner (`batch_done` marker). The batch view
   itself is `/changes?batch=` exactly as designed.
3. **The chronicle collapse keys on `bulk:` correlation ids specifically** — request-level
   correlation ids (`req-…`) exist on many unrelated single events and must never group them.
   Single-event `bulk:` groups render unchanged.
