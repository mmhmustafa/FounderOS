# PR-178.2A — Change Annotation Identity & Scope Isolation

**An Action in One Operational Scope Must Not Silently Change Another.**
*Audit + domain identity review + migration architecture. No code was modified. Nothing was
committed.*

Traced and measured against HEAD `6388dff` and purpose-built multi-scope workspaces.

---

## 1. Executive verdict

The defect is real, reproducible, and worse than "a hash is missing a field" — but the repair is
smaller than expected, because **Atlas already owns every piece of infrastructure it needs**.

Four measurements decided the architecture:

1. **Enterprise has no change data of its own.** It concatenates each profile scope's
   `change_report.json`. Measured: with the same delta in two profiles, Enterprise renders **two
   rows carrying the same DOM `id`** — the duplicate rows already exist today; only their
   *identity* is collapsed. Enterprise is therefore an **aggregate view, not an identity**.
2. **The row already knows its network — but as a display label, not a stable id.**
   `unified_rows(network=scope.label)` carries "Hyderabad", while the stable, rename-proof
   identifier `scope.scope_id` (== `profile_id`) is right there and unused. Measured:
   `profile_id_for("Hyderabad")` = `hyderabad`, and `update_profile` documents *"A rename keeps
   the stable `profile_id`"*.
3. **Stored annotations carry no provenance at all.** A `change-ack` record is
   `{acknowledged, updated_at, updated_by}` — no scope, no network, no device, no change fields.
   The audit event has a `scope_id` field, but `AnnotationStore` never passes it, so **every**
   annotation audit event records `scope_id="all"`. **The original scope of an existing annotation
   is unrecoverable.**
4. **Nothing in the codebase parses a change subject.** It is an opaque key in exactly six places
   (DOM id, URL fragment, annotations key, audit subject, CSV column, one test asserting the
   `change:` prefix). Versioning the format is cheap.

**Verdict: proceed, with a design whose correctness does not depend on the migration succeeding.**

> Identity becomes `change:v2:<scope_id>:<content-hash>`. All **writes** use it, so after this PR
> **no operator action in one scope can ever mutate another scope's record**. Legacy unscoped
> records stay readable through a read-time fallback, so nothing becomes invisible and nothing is
> silently reinterpreted. A startup migration then *converges* the unambiguous legacy records —
> and if it never runs, runs twice, or dies halfway, the system is still correct.

The one consequence that must be accepted deliberately, not discovered later: **two profiles
observing the same device produce two annotatable changes.** Atlas federates *devices*, not
*changes* — there is no change-federation layer anywhere in the repository. This PR does not create
those duplicate rows (they already render); it stops them from sharing one annotation.

## 3. Measured reproduction of cross-scope coupling

Two profiles, the identical topology delta in each:

```
scope=hyderabad      rows=1   subjects: ['change:b8bffe434ac91a0a5054']
scope=secunderabad   rows=1   subjects: ['change:b8bffe434ac91a0a5054']
scope=all            rows=2   subjects: ['change:b8bffe434ac91a0a5054',
                                         'change:b8bffe434ac91a0a5054']
Enterprise renders DUPLICATE DOM ids? True   (2 rows, 1 unique)
Enterprise has its own change_report.json?   False
```

Acknowledging **once**, from Enterprise:

```
annotation records written: ['change:b8bffe434ac91a0a5054']   (one)
scope=hyderabad      → acknowledged
scope=secunderabad   → acknowledged      <-- never chosen by the operator
```

Also measured, and relevant: the same delta re-observed later keeps its subject (durability works
as designed), while a *different* delta (`3 → 4` after `2 → 3`) produces a different subject, so a
recurring-but-changed condition is never silently pre-acknowledged.

## 4. Domain definition of "same change"

| Question | Answer | Basis |
|---|---|---|
| Same delta, same profile, rediscovered tomorrow | **The same annotatable change** | Deliberate durability; an acknowledgement must survive re-discovery. Preserved unchanged. |
| Same delta, *different* before/after next time | **A new change** | Content addressing already gives this; measured. |
| Same delta, two independent networks | **Two changes** | A change report is produced by comparing two consecutive runs **of one profile**. It is literally "what this observation point saw change". Two networks are two operational realities with two owners, two maintenance windows and two on-call rotas. |
| Same delta, one network, two observation profiles | **Two changes** (accepted consequence, §7) | Atlas federates devices, not changes. Inventing a merge here would be a new domain layer. |
| Same delta, seen through Enterprise | **Not a change of its own** — it is the scoped change, viewed | Enterprise has no reports; measured. |

**A change is an observation of a difference made by one observation point.** Identity =
*(who observed it) × (what the difference is)*. Today Atlas stores only the second half.

## 5. Scope / profile / network identity analysis

| Candidate | Stable across rename? | Stable across report regeneration? | Verdict |
|---|---|---|---|
| `scope.label` / `row["network"]` (display name) | **No** — "Hyderabad" → "Hyderabad Production" | yes | **Rejected** — an unstable presentation label |
| `scope.scope_id` (== `profile_id`) | **Yes** — measured; `update_profile` keeps the id | yes | **Chosen** |
| Discovery session / run id | n/a | **No** — changes every run | Rejected (destroys durability) |
| Canonical device id | — | — | Already inside the content hash via `device`; not an isolation boundary |
| Enterprise (`all`) | — | — | Not an identity at all (§6) |

`scope_id` is also exactly the directory that owns the data
(`<output>/.atlas/profiles/<profile_id>/`), the value already carried in `?scope=`, and the value
`_scope_from_next` already validates. It is filesystem-safe (`[a-z0-9-]`), so it is safe in a DOM
`id`, a URL fragment and a JSON key.

The legacy default scope (`scope_id="default"`, "Local workspace") is a first-class scope for this
purpose and gets the same treatment.

## 6. Enterprise aggregation semantics — **Model A (view alias)**

**Enterprise is an aggregate view over scoped facts, and therefore has no annotation identity of
its own.** An Enterprise row carries the subject of the scope that produced it; acknowledging from
Enterprise acknowledges *that scoped change*, and only that one.

Measured basis: Enterprise owns no `change_report.json`; `_change_rows_for` iterates
`aggregation_scopes(scopes)` and concatenates each scope's own reports.

- **Model B (independent identity)** rejected: Enterprise would need its own change data, which
  does not exist. An "Enterprise acknowledgement" would be an annotation on a row that no report
  produced.
- **Model C (propagation)** rejected: acknowledging in Enterprise would fan out to every
  contributing scope — precisely the silent cross-scope mutation this PR exists to end.
- **Model A** additionally repairs the duplicate-`id` HTML defect for free: two rows from two
  scopes become two distinct subjects, hence two distinct ids, independently annotatable.

---

## 7. Multiple-profile semantics

Two profiles observing device R1 canonicalise to **one device** but produce **two change reports**,
each recording what that observation point saw. Under the new contract that is **two annotatable
changes** with distinct subjects.

This is the brief's warned-about "opposite defect", and it is accepted deliberately for three
measured reasons:

1. **The duplication already exists.** Enterprise already renders both rows (measured: 2 rows).
   This PR changes their identity, not their number.
2. **There is no change-federation layer to merge them.** Device federation exists
   (`enterprise/`, identity resolution); nothing equivalent exists for changes. Inventing one is a
   different, larger PR — and the brief forbids redesigning canonical device identity here.
3. **Merging would be a guess.** Two observation points can legitimately disagree about timing,
   values, and whether a change is even visible. Collapsing them would assert an equivalence
   Atlas has not established.

**Recorded as a future PR:** *Change Federation* — deduplicate identical deltas across profiles
observing the same network, with the same evidence discipline device federation uses. Until then
Atlas shows both, and each is annotated where it was observed.

## 8. Proposed identity contract

> A change's annotation identity is **the observation point that reported it, plus the exact
> difference it reported**.

| Property | Rule |
|---|---|
| **Durable across** | re-discovery, report regeneration, restart, profile **rename**, row ordering, page/filter/sort |
| **New identity when** | any of `kind, category, device, field, before, after, description` changes; or the observing scope differs |
| **Never derived from** | display labels, run ids, timestamps, page position, Enterprise |
| **Enterprise** | carries the originating scope's identity; never mints its own |
| **Writes** | always scoped — an action in scope A can only ever write scope A's record |
| **Reads** | scoped record first; unscoped legacy record as an explicit, read-only fallback (§12) |

## 9. Proposed subject format

```
change:v2:<scope_id>:<sha256(kind|category|device|field|before|after|description)[:20]>

e.g.  change:v2:hyderabad:b8bffe434ac91a0a5054
```

- **Explicitly versioned.** Justified by measurement, not neatness: nothing parses the subject, so
  the cost is nil; the prefix makes v1 and v2 distinguishable *by eye* in `annotations.json` and
  the audit log; it gives the migration a free idempotency check; and it prevents any accidental
  collision between old and new semantics.
- **Scope in cleartext.** It makes `/audit?subject=hyderabad` a useful filter, makes a
  mis-attribution visible during review, and costs nothing — scope ids are already in every URL.
- **Character safety.** The subject already contains a colon today and works as a DOM id and URL
  fragment; two more change nothing. No JavaScript resolves elements by this id (verified), so no
  CSS-escaping hazard is introduced.
- The content basis is **unchanged**, so the durability property is preserved exactly.

## 12. Migration feasibility

Migration is **feasible but not universally decidable** — so the architecture is built so that
**correctness never depends on it**:

- **Correctness** comes from two rules that need no data change: *writes are always scoped*, and
  *reads fall back to the unscoped legacy key*. Apply only these and the system is already correct:
  no operator action can cross scopes again, and no existing annotation disappears.
- **The migration is a convergence step**: it rewrites the legacy records whose scope is provable,
  shrinking the fallback set toward zero.

Consequences of that framing (all verified against the existing machinery):

- If the migration never runs → correct, with more legacy records.
- If it runs twice → idempotent (a v2 key already present is skipped).
- If it dies mid-way → `annotations.json` is written by temp-file-plus-atomic-replace, and the
  schema version is stamped only afterwards, so it simply re-runs.
- If it runs before the reports exist → it resolves nothing and leaves everything to the fallback.

**Options evaluated:** hard cutover (**rejected** — silently drops live operator state);
automatic deterministic migration (**adopted, for the unambiguous class only**); lazy
read-time write (**rejected** — a GET must not mutate the workspace); compatibility alias
(**adopted, read-only, for the residue**); versioned identity (**adopted**, §9).

## 13. Migration strategy by annotation kind

| Kind | Unambiguous (exactly one scope renders it) | Ambiguous (2+ scopes) | Unresolvable (0 scopes) |
|---|---|---|---|
| `change-ack` | **Move** to `change:v2:<scope>:<hash>` | **Leave as legacy** — copying would assert an acknowledgement the operator never made, and would hide a genuine change from an "unacknowledged" filter in a scope nobody chose | Leave untouched |
| `change-assignment` | **Move** | **Leave** — assigning work to the wrong site's owner manufactures false accountability | Leave |
| `change-note` | **Move** | **Leave** — a note is site-specific context; duplicating it fabricates a statement about another network | Leave |
| `change-suppression` | **Move** — and note that moving strictly *reduces* hiding: the v1 record hid the change in **every** scope, the v2 record hides it in **one** | **Leave**, and **report it prominently**: this is the only kind whose non-migration is operationally visible, because the fallback keeps hiding rows in every scope until the operator acts | Leave |

The per-kind difference is therefore real and load-bearing: **the ambiguous rule is uniformly
"never invent an operator decision", but the justification and the reporting differ**, and
suppression alone is singled out for prominence because it is the only kind that removes evidence
from view.

## 14. Ambiguous migration handling

**Ambiguous records are never copied, never split, never guessed at, and never deleted.** They
remain under their v1 key and remain visible through the read-only fallback — which means their
*display* behaviour is unchanged (still shared across scopes, exactly as today), while their
*mutation* behaviour is fixed (any action now writes a scoped v2 record).

Convergence without a decision: the first time an operator acts on such a row in a scope, that
scope gets its own v2 record, which takes precedence there. The legacy record keeps serving the
scopes nobody has acted in — and Atlas can say exactly that.

The migration reports counts per class and per kind in its audit event, so the operator can see
how much state is still unscoped.

---

## 15. Workspace / schema versioning

**Use the existing ladder. Do not invent `annotation_identity_version`.**
`workspace/migrations.py` already provides everything the brief asks for: an ordered registry, a
recorded version in `workspace-schema.json`, a mandatory **backup to
`migration-backups/v<N>/` before touching a file**, an idempotency contract, and an audit event —
written with `actor="system", source="startup"`, which the chronicle already classifies as
`system` and therefore keeps **out of the operator Timeline** while leaving it in `/audit`.

This PR registers **migration v3**. One plumbing change is required and it is small: the migration
needs the **output** directory (where the change reports live) as well as the **workspace** root —
two different trees. `create_app` already has both in scope at the call site
(`migrate_workspace(resolved_workspace)`, with `resolved_output` on the line above), so the
`Migration.apply` signature gains a context argument that the two existing migrations ignore. When
the output directory is absent (a CLI path), v3 resolves nothing and leaves the fallback to do its
job — which is safe by construction (§12).

---

## 16. New-workspace behaviour

A new workspace has no `change-*` annotations, so v3 resolves nothing and stamps the version. Every
subject minted from the first discovery onward is `change:v2:<scope_id>:<hash>`. The read-time
fallback never fires because no unscoped record exists. **Nothing to explain to a new user.**

---

## 17. Existing-workspace upgrade behaviour

**No operator is asked to delete a workspace, and nothing is lost.** On first start after the
upgrade:

1. Annotations are backed up to `migration-backups/v3/annotations.json`.
2. Unambiguous legacy records are moved to their scoped key.
3. Ambiguous and unresolvable records stay exactly where they are and keep displaying through the
   fallback.
4. One audit event records the counts by class and kind; per-record moves are audited individually
   with `actor="system"` so `/audit` explains every remap without flooding the Timeline.

**What an operator could notice:** nothing changes visually for unambiguous records. For ambiguous
records, behaviour is unchanged until they act — and from that point the annotation applies only
to the scope they acted in, which is the entire point of the PR. No acknowledgement, owner, note
or suppression disappears at any stage.

---

## 18. Audit-history behaviour

**Historical audit events are never rewritten.** They keep their v1 subjects, their timestamps and
their actors. An investigator distinguishes eras by the prefix: `change:<hash>` is pre-isolation,
`change:v2:<scope>:<hash>` is post-isolation, and the migration's own events explain the mapping
between them. Cosmetic consistency is explicitly sacrificed to historical truth.

One forward improvement lands with the new writes: because the bulk/annotation paths will know
their scope, new annotation audit events can finally carry a real `scope_id` instead of `"all"`
(the defect recorded as D4 in the PR-178.2 review).

---

## 19. Timeline behaviour

Existing chronicle rows link to `/changes#<v1 subject>`. After migration that fragment matches no
row, so the browser simply does not scroll — the page still loads correctly. This is graceful and
**historical chronology is not rewritten**. New rows link to the v2 subject and anchor exactly.

## 20. Scope rename / delete / recreate behaviour

| Event | Behaviour | Basis |
|---|---|---|
| **Rename** ("Hyderabad" → "Hyderabad Production") | Annotations survive untouched | `profile_id` is stable across rename (measured + documented in `update_profile`) |
| **Delete a profile** | The profile record and its credential are removed; **the scope's artifact directory is not deleted** — that is what the orphan-scope feature exists to reclaim | `delete_profile` removes only the repository entry and credential |
| **Recreate with the same name** | Gets the **same** `scope_id` (`_unique_profile_id` re-uses a freed slug) and the same directory, so old annotations re-attach to identical deltas | measured: `profile_id_for("Hyderabad")` = `hyderabad` both times |

Re-attachment after delete/recreate is **coherent, not a leak**: the evidence was never deleted
either. It is recorded, not hidden. A per-incarnation id was **rejected** — it would be invisible
to the operator and would break the far more common rename case's intuition. **Recorded as a
follow-up product decision:** whether deleting a profile should also delete that scope's
annotations, so "delete" means the same thing for evidence and for operator state.

## 21. Rollback strategy

| Mechanism | Guarantee |
|---|---|
| Pre-migration backup | `migration-backups/v3/annotations.json`, written before any change (existing ladder behaviour) |
| Rollback procedure | copy the backup back; set `workspace-schema.json` to `{"version": 2}` |
| Reverting the code alone | Safe even **without** restoring: v2 keys are simply never matched by v1 code, and un-migrated legacy records still work |
| Idempotency | Re-running skips records that already have a v2 twin |
| Crash safety | Atomic temp-file replace for the data; version stamped only after success |
| Destructive rewriting | **None** — records are moved within one file, with a backup; nothing is deleted, no evidence is touched |

## 22. Security / trust analysis

| Threat | Before | After |
|---|---|---|
| Cross-scope mutation from a normal UI action | **Real and measured** | **Eliminated for all new writes**; legacy display sharing is explicit and decays |
| Forged subject id | Accepted, writes a durable orphan (measured) | The scoped subject makes "does this subject render in the scope I am working in?" a **meaningful** check — PR-178.2's validation rule finally has teeth |
| Subject from another scope | Indistinguishable from my own | Distinguishable by construction; rejected by the same rule |
| Enterprise as an escalation path | Ambiguous | Enterprise rows are scoped rows; an Enterprise action mutates exactly one scope's record |
| Deleted/recreated profile | Silent re-attachment | Same behaviour, now documented and bounded (§20) |
| Legacy v1 ids | Full cross-scope reach | Read-only; can never be *written* again |
| Migration as an attack surface | — | Runs as `system` at startup, transforms metadata only, backed up, idempotent |

**The trust boundary is now the scope**, and it is enforced at the point of writing rather than
hoped for at the point of display.

## 24. PR-178.2 bulk implications

The scenario the brief demands, answered unambiguously:

1. 50 changes selected in Hyderabad → 50 subjects `change:v2:hyderabad:<hash>`.
2. The same logical deltas in Secunderabad are `change:v2:secunderabad:<hash>` — **different
   subjects, untouched**.
3. Enterprise renders both sets, now with **distinct** DOM ids (the duplicate-id defect is gone).
4. Bulk-suppress from Hyderabad → **exactly those 50 Hyderabad records** are suppressed.
5. Opening Enterprise: the 50 Hyderabad rows are hidden with *"50 suppressed change(s) hidden"*;
   the 50 Secunderabad rows still show, unsuppressed.

Bulk also inherits a genuinely enforceable scope check (§22), which is why this PR must land
**first**: without it, one bulk action can silently mutate up to 200 records in scopes the
operator never opened.

## 25. Test strategy

**Identity** — the fingerprint is unchanged for identical content in one scope (durability);
different scopes yield different subjects; a rename preserves subjects; a changed `before`/`after`
yields a new subject; Enterprise rows carry their originating scope's subject; two scopes with the
identical delta render two **distinct** DOM ids; the subject is a valid DOM id and URL fragment.

**Isolation** — acknowledging/assigning/suppressing/noting in scope A leaves scope B's row
untouched, per kind; acting from Enterprise mutates exactly one scoped record; a subject from
another scope is not accepted by the scope in which it is posted.

**Fallback** — a legacy unscoped record still displays in every scope that renders the content;
acting on it writes a **v2** record; the v2 record takes precedence in its own scope; the legacy
record is never written to again.

**Migration** — unambiguous records move, per kind; ambiguous records are left untouched, per
kind; unresolvable records are left untouched; re-running changes nothing; running with no change
annotations does nothing; running with no output directory resolves nothing and stays safe;
`migration-backups/v3/annotations.json` exists and restores; the audit event carries per-class and
per-kind counts; per-record migration events are `actor="system"` and therefore absent from the
default Timeline but present in `/audit`; a crash before the version stamp re-runs cleanly.

**History** — no historical audit event is modified; a chronicle row linking to a v1 fragment
still loads.

**Regression** — Changes filters, comparison mode, CSV export, saved filters, pagination,
single-row workflows and the full suite.

## 29. Adversarial review findings

Performed against the architecture above, before presenting it. **Three findings changed the
design**; all amendments are folded into §1–§28.

**29.1 — BLOCKER (amended): "retain v1 + read-time fallback" reopened the leak for *migrated*
records.** The first draft was purely additive: write v2, keep v1, fall back to v1 on a miss.
Attack: an unambiguous suppression is migrated to `hyderabad`; later a *new* discovery makes
Secunderabad report the identical delta; Secunderabad's v2 key misses, the fallback finds the
retained v1 record, and the change is silently suppressed in a scope nobody decided about — the
original defect, resurrected months later. **Amendment:** the migration **moves** unambiguous
records (removing the v1 key) and **leaves** ambiguous/unresolvable ones, so the fallback set is
exactly the records Atlas cannot attribute. The pre-migration backup preserves reversibility.

**29.2 — BLOCKER (amended): a startup migration cannot see the change reports.**
`migrate_workspace(workspace_root)` receives only the workspace tree; the reports live under the
**output** tree (`<output>/.atlas/profiles/<id>/change_report.json`). The draft's v3 migration
would have resolved *nothing* and then stamped the version, permanently skipping the remap.
**Amendment:** the ladder passes an output-directory context (available at the call site), **and**
— more importantly — the architecture was restructured so the migration is a *convergence* step
rather than a correctness requirement (§12), so a context-less run is safe rather than
irreversible.

**29.3 — HIGH (amended): the "network" already on the row is the wrong identifier.** The obvious
implementation is `unified_rows(network=…)` → put `network` in the hash. Measured: `network` is
`scope.label`, the **display name**. Renaming a profile would have invalidated every annotation in
it. **Amendment:** identity uses `scope.scope_id` (`profile_id`), verified stable across rename;
`unified_rows` gains an explicit `scope_id` parameter rather than reusing `network`.

**Attacks that did *not* change the design** — recorded so they need not be re-run:

- *Enterprise aliasing* — Enterprise owns no reports (measured), so Model A is the only model that
  does not invent data; and it repairs the duplicate-`id` defect as a side effect.
- *Two profiles, one canonical device* — the duplicate rows already render today (measured); this
  PR changes their identity, not their count. Accepted and recorded as Change Federation (§7).
- *Scope rename* — `profile_id` is stable (measured).
- *Delete/recreate* — same slug, same directory, artifacts never deleted; coherent and documented
  (§20).
- *Suppression migration danger* — moving a suppression **reduces** its blast radius from every
  scope to one; the migration cannot make suppression worse.
- *Ambiguous migration* — never copied, never guessed; display behaviour is unchanged and decays on
  first action.
- *Forged and stale legacy ids* — legacy ids become read-only; the scoped subject is what finally
  makes PR-178.2's existence check a real boundary.
- *Rollback / restart / duplicate run* — backup, atomic replace, stamp-after-success, and a v2-key
  idempotency check (§21).
- *Audit history* — never rewritten; migration events are `actor="system"` and are therefore
  already excluded from the operator Timeline by the existing chronicle rule.
- *Performance* — four extra dict lookups per row; a one-off startup pass that is skipped when no
  change annotations exist.

## 31. FINAL APPROVED IMPLEMENTATION PLAN

**Step 1 — Identity (pure functions, no I/O).**
Add `change/identity.py`: `content_hash(row)` (today's basis, unchanged), `subject_v1(row)`,
`subject_v2(row, scope_id)`, and `resolve_annotation(records, subject_v2, subject_v1)` — the ONE
place that implements "scoped record first, unscoped legacy fallback". Give `unified_rows` an
explicit `scope_id` parameter; `finish()` mints the v2 subject and also carries `subject_legacy`
on the row for the resolver.
*Tests:* durability, per-scope distinctness, rename stability, content sensitivity, resolver
precedence.

**Step 2 — Wire the two producers and every consumer.**
`_change_rows_for` passes `scope.scope_id` per scope; `changes_compare` passes the scope that owns
the left snapshot. `annotate_rows` and `changes_annotate`'s previous-owner lookup use the resolver.
Every **write** uses the v2 subject only — so from this commit, no action in one scope can mutate
another's record.
*Tests:* the isolation matrix per annotation kind; Enterprise acts on exactly one scoped record;
two scopes render two distinct DOM ids; the legacy fallback displays and then decays.

**Step 3 — Migration v3 (convergence).**

*Tests:* the three classes per kind; idempotency; no-output-dir safety; crash-before-stamp re-run;
backup exists and restores; no historical audit event is modified.

**Step 4 — Validate.**
Full suite; the browser plan in §26; a rename cycle; a delete/recreate cycle; and an explicit
