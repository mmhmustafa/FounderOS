# PR-178.2A — Implementation Handover

**Change Annotation Identity & Scope Isolation.**

Implemented exactly per the approved architecture review's §31 plan (with its three adversarial
amendments). Validated against the full suite, a purpose-built two-profile world driven through
the real server — including a live startup migration — and the live estate for performance.

---

## 1. Executive result

An action in one operational scope can no longer silently change another. Change annotation
identity is now *the observation point that reported the change plus the exact difference it
reported* — `change:v2:<scope_id>:<content-hash>` — with the content basis byte-identical to the
old fingerprint, so rediscovery durability is unchanged. Every write is scoped; pre-isolation
records remain readable through one canonical read-only fallback and decay per scope on the first
action there; a startup migration moved the provably-attributable legacy records and refused to
guess about the rest. Enterprise mints no identity of its own, which also removed its measured
duplicate-DOM-id defect. History was not rewritten anywhere.

## 4. Final identity contract

A change's annotation identity = *(who observed it) × (what the difference is)*.
Durable across rediscovery, report regeneration, restart, profile rename, ordering. New identity
when any of `kind, category, device, field, before, after, description` changes, or the observing
scope differs. Never derived from display labels, run ids, timestamps, or Enterprise.

## 5. Subject format

`change:v2:<scope_id>:<sha256(kind|category|device|field|before|after|description)[:20]>` —
e.g. `change:v2:hyderabad:c7560f6ac233a1c2908f`. `change/identity.py` is the only place that
knows the layout (`content_hash`, `subject_v1`, `subject_v2`, `subject_v2_for_hash`, `parse_v2`,
`scope_of`, `legacy_subject_of`, `resolve_annotation`). Pinned: the content basis equals the v1
basis exactly (`change_fingerprint(row) == subject_v1(row)`), so migration matching and
durability are guaranteed by the same test.

## 6. Cross-scope defect — before / after (measured)

**Before** (architecture review §3, reproduced): the identical delta in Hyderabad and
Secunderabad shared subject `change:b8bffe…`; acknowledging once from Enterprise wrote ONE record
and both scopes rendered "acknowledged". Enterprise rendered two rows with the same DOM id.

**After** (browser-validated on the two-profile world): the shared delta renders
`change:v2:hyderabad:c7560f…` and `change:v2:secunderabad:c7560f…`. Acknowledging Hyderabad's row
left Secunderabad's twin unacknowledged — verified by DOM parse of both scope pages, and
re-verified after a server restart. The audit event for an Enterprise-initiated action records
the *originating* scope (`scope_id="hyderabad"`), pinned by test.

## 7. Enterprise semantics

Model A (view alias), as approved: Enterprise owns no change data and mints no subjects; each
aggregated row keeps the scope that produced it. Acting from Enterprise mutates exactly that one
scoped record (pinned + browser-validated: suppressing Secunderabad's row from the Enterprise
view hid it in Secunderabad only; Hyderabad's hidden count stayed 0). Duplicate Enterprise DOM
ids: measured 4 rows / 4 distinct ids where the old identity produced 2 rows / 1 id.

## 8. Multiple-profile consequence (accepted, recorded)

Two profiles observing the same canonical device produce two annotatable changes — the rows
already both rendered before this PR; only their identity was collapsed. No deduplication was
invented. **Future PR — Change Federation** remains the recorded follow-up.

## 9. v1/v2 resolver behaviour

`resolve_annotation` is the single implementation of precedence: scoped record → legacy record →
nothing. Used by `annotate_rows` (all four kinds) and the previous-owner lookup in
`changes_annotate`. Reads never write (pinned: two full page renders leave `annotations.json`
byte-identical). Legacy records display in every scope that renders their content — exactly
today's behaviour — until someone acts.

## 10. Single-row write behaviour

Every write in `/changes/annotate` uses the posted v2 subject. Un-acting on state that only a
legacy record asserts writes a scoped **negative shadow** (`{"acknowledged": False}` /
`{"suppressed": False}`) instead of touching the read-only legacy record; `annotate_rows` honours
the explicit negative while plain presence keeps meaning what it always did. Browser-proven: un-
suppressing the legacy-suppressed shared row in Hyderabad revealed it there (hidden count 0)
while Secunderabad kept hiding it. Pinned: after any action, no `change-*` annotation key is ever
a v1 subject; the legacy record's bytes and provenance (`updated_by`) are untouched.

## 11–12. Migration v3 behaviour + real counts

The ladder gained a context (`output_dir` — artifacts live in a different tree than the
workspace); the two existing migrations ignore it. v3 classifies each legacy `change-*` subject
against the content each live scope currently reports (saved profiles incl. archived + the
default scope; orphan directories excluded — nothing renders them):

| Class | Action | Validation-world result (real startup, not a harness) |
|---|---|---|
| UNAMBIGUOUS | **moved**, v1 key removed | `change-ack` → `change:v2:hyderabad:a68c…`, `updated_by=pre-isolation-operator` preserved |
| AMBIGUOUS | left legacy | the shared-delta suppression stayed `change:c756…`; summary counted it |
| UNRESOLVABLE | left legacy | pinned by test |
| destination v2 exists | never overwritten; legacy kept | pinned by test ("newer scoped operator state wins") |

Summary audit event: `{"change-ack": {moved: 1, …}, "change-suppression": {ambiguous: 1, …}}` —
exactly the seeded truth. Ambiguous suppression is visible in the counts, per the architecture's
prominence requirement, and remains operationally visible (it kept hiding the row in both scopes
until the operator acted in one).

## 13. Backup / idempotency / crash safety

`migration-backups/v3/annotations.json` written before any rewrite and verified byte-identical
to the pre-migration file (test + validation world). Re-run: idempotent (pinned). Crash before
stamp: version marker deleted and re-run — annotations byte-identical, version re-stamped
(pinned). Contextless run (`output_dir=None`): nothing attributed, nothing touched, and the
summary event says "nothing was attributed" (pinned). Rollback = copy the backup back and set the
schema version to 2; reverting the code alone is also safe (v2 keys are simply unmatched by v1
code paths — but they exist only for new writes, which old code would not have made).

## 14. Audit-history behaviour

**Historical audit was NOT rewritten** — pinned by a byte-prefix assertion: after migration,
`audit.jsonl` *starts with* the exact pre-migration content. New per-move events carry
`actor="system"`, `source="startup"`, the resolved `scope_id`, and before/after subjects; the
summary event carries the per-kind/per-class counts. New operator writes now record the real
scope instead of the historical constant `"all"` (the D4 defect, fixed for this path).

## 15. Timeline behaviour

Migration events are system-classified (pinned against `chronicle_events`) so they stay out of
the default operator chronology while `/audit` retains everything. Historical chronicle rows
linking `/changes#change:<oldhash>` load safely; the fragment no longer scrolls after a move
(accepted, per spec — no alias routing was added). New rows anchor exactly.
