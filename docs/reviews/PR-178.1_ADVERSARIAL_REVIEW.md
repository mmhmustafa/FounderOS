## 2–4. Challenged assumptions, evidence, and new blockers

### B1 — "The menu list escapes its scroll container" is impossible with absolute positioning

**The claim under attack** (§10 Step 1, §17): fix clipping while preserving horizontal scrolling.

**Evidence — a hit test, not an opinion.** With the last row's menu open, I probed a point
inside the menu's own bounding rect but below the scroller's bottom edge:

```
position: absolute → elementFromPoint(1104, 716) === SUMMARY        // menu NOT painted there
position: fixed    → elementFromPoint(1127, 716) === action-menu-item // menu IS painted there
ancestors creating a fixed containing block (transform/filter/contain): []
```

An absolutely positioned box is clipped by any ancestor with `overflow != visible` on its
containing-block chain. `.action-menu` is `position: relative` and lives *inside*
`.table-scroll`, so the scroller is on that chain. **No amount of CSS on `.action-menu-list`
can escape it** while the menu's containing block remains inside the scroller. The document's
Step 1 — "a behaviour/CSS layer fix, no template churn" — cannot deliver what it promises.

**Required amendment.** The fix needs one of: (a) **`position: fixed` with JS-computed
coordinates** on open, flipping near the right/bottom edges, plus close-or-reposition on scroll;
(b) the native `popover` attribute (top layer, escapes all clipping) — but it wants
`popovertarget` on a `<button>`, which conflicts with `<details>/<summary>`, and its support in
the target environment is unverified; (c) moving the menu markup outside the scroller (a portal),
which server-rendered Jinja makes awkward and which breaks the row/menu association.

**Recommendation: (a), as progressive enhancement.** The CSS stays `position: absolute` so the
no-JS baseline is exactly today's behaviour (opens, may clip — *no regression*); JS switches the
**open** list to `position: fixed` at computed coordinates. Verified safe: there are **zero**
transform/filter/contain ancestors, so `fixed` resolves against the viewport. This is materially
more work than "a CSS fix" and Step 1 must be re-scoped to say so.

### B2 — Form actions inside `entity_menu` produce invalid nested forms

**The claim under attack** (§10 move 2, §26): `entity_menu` gains form-action support.

**Evidence.** `policy.html:256` opens `<form method="post" action="/policy/assign">`; the
results table is lines 259–293; the `entity_menu` call is **line 288 — inside that form**.
`evidence_index.html:193` opens `<form method="post" action="/evidence/bulk-export">` and its
table (194–231) contains the row actions at line 215.

HTML forbids nested `<form>`. The parser **drops the inner form entirely**, so its controls
become children of the outer form — a click intended for `/changes/annotate` would POST to
`/policy/assign` or `/evidence/bulk-export`. This is worse than a layout bug: it is a silent
mutation sent to the wrong endpoint.

**Required amendment.** The macro must **not** accept a generic form parameter usable anywhere.
Either (i) restrict form actions to call sites proven form-free, enforced by a test that fails if
a table wrapped in a `<form>` renders a form-bearing menu; or (ii) use the HTML5 `form="id"`
attribute so the control is *associated* with a form declared outside the table, with no nesting.
**(ii) is the smaller, safer primitive** and it also unblocks B3.

### B3 — Steps 3 and 4 are mutually incompatible

**The claim under attack** (§26, §28 Step 4): give Changes selection and a bulk bar.

**Evidence.** `changes.html`'s table (line 159) is **not** wrapped in a form today, which is
precisely why its four per-row POST forms (lines 196–235) are valid. Adding bulk selection the
way Policy and Evidence do it — wrapping the table in `<form method="post">` — would nest those
four existing forms inside it and **break acknowledge / assign / note / suppress, which work
today**. The plan would regress live capability in the name of adding a convenience.

**Required amendment.** If Changes gains selection, the bulk form must live **outside** the
table with checkboxes bound by `form="changes-bulk"`. Verified compatible: the selection engine
queries `tbody input[type=checkbox][name=…]` and never inspects form ancestry
(`atlas.js:1490-1494`), and its count lookup falls back to `document` when the table has no form
ancestor (`atlas.js:1506`).

### B3b — …and Changes bulk needs new backend semantics regardless

`/changes/annotate` reads a **single** `subject` (`routes.py:5174`) and flashes one message. It
is definitively a single-row endpoint. Safe multi-row acknowledge/assign/suppress needs, at
minimum: `getlist("subjects")`, per-subject eligibility (acknowledge vs unacknowledge, suppress
vs unsuppress are mutually exclusive **per row**, so a mixed selection has no single correct
action), one audit record per subject under one correlation id (the pattern `/policy/assign`
already uses at `routes.py:3686`), partial-failure accounting, the required-owner and
required-reason validations applied per batch, and duplicate-submission protection.

**Decision: Changes bulk is NOT presentation work. It is removed from PR-178.1** and recorded as
its own PR. This also dissolves B3's incompatibility for this PR.

## 5. Corrections to false statements in the architecture document

**C1 — the selection count.** §8 states the bulk bar "appears only when the selection is
non-empty (the count element is empty otherwise, which is already the JS behaviour)". Reading
`atlas.js:1506-1512`, the hook does exactly one thing:

```js
count.textContent = checked ? checked + " of " + boxes.length + " selected" : "";
```

It sets **text**, never visibility. Nothing in the engine hides or shows a bar. Any
"appears when non-empty" behaviour is **new JS that PR-178.1 must own**. Also verified:
`syncHeader` runs only on `change` events and on select-all — **never on page load**, so a
browser-back restoring checked boxes from bfcache leaves the count and the `.row-selected`
outlines stale. Select-all, deselect-all and indeterminate are correctly implemented
(`atlas.js:1494-1502`); filter/sort/pagination are server re-renders, so selection correctly
does not survive them.

**C2 — the scope of the duplication.** §7 and §20 claim five `device_actions` capabilities are
duplicated in table rows. In rows, `device_actions` is called with `compact=True`, and the
Configuration / Investigate / Predict trio renders **only when `not compact`**
(`_device_actions.html:76-83`). So in table rows the macro emits **SSH console, Copy SSH, and
web** — of which only the two SSH actions are duplicated in `entity_menu`; **web management is
unique**. The five-way duplication is real but only on `device.html:23-24`, a **detail page the
plan explicitly leaves unchanged**. The document cited it as motivation for a change that does
not address it.

## 6. Remaining challenges, answered

**§5 Permissions.** The rule (unauthorized → omit; not-applicable → greyed with reason) is
determinable without new per-row work: `can()` is a template global already used per row on
Evidence (`evidence_index.html:193,194,215`), and eligibility already rides on the
request-cached target. **But Policy does not follow it**: `policy_assign` requires
`POLICY_MANAGE` (`authz_map.py:156`) while `policy.html:262,272,296` render the select-all, all
50 checkboxes and the assign form **ungated** — a viewer gets 50 dead checkboxes and a form that
will 403. That is the exact pattern PR-178 removed from Evidence. **Amendment A2: gate Policy's
selection column and assign form on `can('policy.manage')`.** No information-disclosure problem
was found in greyed not-applicable items: their reasons name absence of local evidence, not
another principal's data — though the reason can be *wrong*, see §7 below.

**§6 Web-management move.** All variants are preserved only if the menu carries every branch:
Open HTTPS (+ cert-flag), Copy HTTPS URL, Open HTTP — Insecure (exact wording, insecure
warning), Copy HTTP URL, and the greyed "Web unavailable" carrying `web.reason`
(`_device_actions.html:52-74`). The data source and per-request cache (`g._web_access`,
`routes.py:9257-9280`) are reused, not duplicated. **Amendment A3:** `device_menu` does **not**
call `web_access` today, and neither do Policy, Timeline, Topology, Predict or incident_case.
Adding a web group to `ACTION_ORDER` would newly trigger the cache build on those five pages, and
that build calls `services_for()` per device, which calls `_load()` — a full file read + parse —
**per device** (`management/store.py:63-72`). Measured on the live estate: **4.7 ms for 85
devices** (0.055 ms each), i.e. real, linear, and small today; ~50 ms at 850 devices. Not a
blocker, but the PR-176 precedent applies: **memoise `_load()` per store instance** in the same
commit, or scope the web group to pages that already resolve web access.

**§7 One-to-one preservation.** Corrected matrix in §12 below.

**§11 Action-column contract.** The universal "one primary link + one menu trigger" does **not**
hold on Timeline: `device_menu()` returns `[]` when a row names no device, and `entity_menu`
correctly renders nothing — measured, Timeline's first row has 1 control (the link) and no
trigger. That is the right behaviour and the contract must be restated as *"one primary link
always; a trigger only when the row has secondary actions"*. No empty triggers are introduced.
Configuration rows have no natural checkbox and none is proposed — fine.

**§13 The 11 px defect.** Independent, confirmed. With the `position: fixed` amendment the menu
no longer depends on the scroller's geometry at all, so the two are **not** coupled. Keep it
separate.

**§14 No-JS baseline.** Without JS: `<details>` opens natively (menu usable, possibly clipped —
today's behaviour); all GET links work; all row POST forms submit with CSRF and `next`; required
inputs are enforced by the browser; individual checkboxes still submit (select-all does not, as
the engine's own comment states). The `position: fixed` enhancement must therefore be applied
**on open by JS only**, never in the stylesheet — otherwise a no-JS menu would be positioned
against the viewport with auto offsets and could land anywhere.

**§10 Step 5 (on-demand DOM).** Attacked and **rejected**. Cloning form markup on first open
must reproduce the CSRF token, required-input validation, unique ids and autofill behaviour, and
would put the no-JS baseline and the JS path on different code paths — for a DOM saving that
matters only on Changes (600 hidden inputs). Steps 1–4 already remove 100–150 controls per page
from Evidence and Configuration. **Skip Step 5.** Revisit only if measurement after Steps 1–4
shows a user-visible problem.

## 7. Newly discovered defect (outside the plan)

`device_entity_actions` accepts `has_evidence` / `has_configuration` but **no caller passes
them** (`linking.py:225-236` vs `routes.py:9349-9356`). When `device_target()` returns `None`,
the menu asserts "no evidence records are stored for X in this scope" and "no configuration is
held for X in this scope" **without having consulted either store**. That is a stated reason
that can be false — an honesty defect of the same family PR-178 spent its budget on. It is
**not** created by this plan; record it and fix it in whichever PR touches `linking.py`.

## 8–11. Explicit decisions

**8. Changes bulk operations — REMOVED from PR-178.1.** It requires new backend semantics
(§B3b) and, as specified, would break working per-row forms (§B3). It becomes **PR-178.2 —
Bulk Change Triage**, which owns the endpoint contract, per-row eligibility in a mixed selection,
correlation ids, partial failure, and the `form="…"` binding.

**9. Semantics — NATIVE DISCLOSURE (Option A). Arrow keys are NOT added.** The ARIA menu pattern
demands `role="menu"`/`menuitem`, roving tabindex, and items removed from the tab order; it is
designed for application commands, not a list of links. Adding arrow keys to a `<details>` while
leaving `<ul><li><a>` inside is precisely the half-menu the brief forbids. **Delete
`role="button"` and `aria-haspopup="menu"` from the summary** so the native disclosure announces
expanded/collapsed correctly, keep the row-aware `aria-label`, keep Tab as the key that moves
through an open menu, keep Escape and focus return. This is a **two-attribute deletion** and it
*removes* work from the plan.

**10. Menu positioning — `position: fixed`, set by JS on open, as progressive enhancement.**
Proven by hit test to escape the clip; proven that no ancestor blocks fixed positioning. CSS
keeps `absolute` as the no-JS baseline. Must flip up near the viewport bottom and align right
near the right edge, and must close (not drift) on scroll of the table or page.

**11. Step 5 on-demand DOM — SKIPPED**, per §6 above.

## 14. FINAL APPROVED IMPLEMENTATION PLAN

**Step 1 — Menu semantics and positioning (the functional fix).**
Delete `role="button"` and `aria-haspopup="menu"` from `entity_menu`'s summary; keep the
row-aware `aria-label`. Add a JS enhancement that, on open, switches the list to
`position: fixed` at computed coordinates, flipping up/left at viewport edges, and closes on
scroll. CSS keeps `absolute` as the no-JS baseline. **No arrow keys.** Tests: un-clipped at
first/middle/last row at 375/768/1440/1920; within viewport at 375; Escape closes and returns
focus; one menu at a time; no-JS still opens.

**Step 2 — Remove the row duplication, without losing web.**
Add a `web` group to `ACTION_ORDER`/`device_entity_actions` reproducing all five branches
verbatim, fed from the existing `g._web_access` cache; memoise `ManagementServiceStore._load()`
per instance; switch **Evidence and Configuration table rows** from `device_actions` to
`entity_menu`; delete the two dead imports (`changes.html:2`, `topology.html:2`). Detail pages
untouched. Tests: the §12 matrix, branch by branch; Evidence tab stops 201 → ≤101; zero accent
buttons in rows; render cost unchanged within PR-176 budgets.

**Step 3 — Selection honesty (no new bulk).**
Gate Policy's select-all, row checkboxes and assign form on `can('policy.manage')`. Render
`[data-selection-count]` beside the existing Policy and Evidence bulk submits, and add the small
JS that shows/hides the bar on non-empty selection — **explicitly new behaviour**, plus a
`pageshow` re-sync. Update `SELECTION_TABLES` deliberately. No changes to bulk endpoints.

**Step 4 — Validate.** Full suite; four widths; viewer / operator / export-capable roles;
keyboard-only; the eight operator tasks; PR-176 recheck.

**Deferred out of this PR:** Changes bulk triage (**PR-178.2**, new backend semantics);
`.table-scroll-wide` 11 px overshoot (own commit); `has_evidence`/`has_configuration` reason
defect (with the next `linking.py` change); on-demand menu DOM (**skipped**, revisit only on
measurement).

**Handover must state:** before/after tab stops and accent-button counts per page; that every
§12 row survived to a named destination; that no POST became a GET and no form was nested; the
measured web-cache cost before and after memoisation; and that Changes bulk was deliberately
deferred rather than dropped.
